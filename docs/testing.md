# ๗. การทดสอบ

หน้านี้คือ **รายการทดสอบที่ต้องทำตาม** — แต่ละข้อมีวิธีตรวจและเกณฑ์ผ่านชัดเจน

::: danger กติกา
1. ทดสอบตามลำดับเลข **ห้ามข้าม**
2. ข้อไหนไม่ผ่าน = **หยุด** แก้ก่อน ห้ามทดสอบข้อถัดไป
3. จดผลจริงทุกข้อ ห้ามเขียนว่าผ่านถ้ายังไม่ได้ทดสอบ
4. ถ้าผิดปกติที่กระทบงานเดิมของพี่ฆัง ให้หยุดทันทีก่อนแก้อย่างอื่น
:::

## กติกาการจดผล

ใช้ตารางนี้ทุกครั้ง

| ผล | ความหมาย |
|---|---|
| ✅ ผ่าน | ทดสอบจริงแล้ว ได้ผลตามเกณฑ์ |
| ❌ ไม่ผ่าน | ทดสอบจริงแล้ว ไม่เป็นไปตามเกณฑ์ |
| ⏳ ยังไม่ได้ทดสอบ | ยังไม่ได้ทำ — ห้ามนับเป็นผ่าน |

::: warning กฎของครอบครัว — ห้ามเดา
ถ้ายังไม่ได้ทดสอบ ให้เขียน "ยังไม่ได้ทดสอบ" ไม่ใช่เดาแล้วเขียนว่าผ่าน
"น่าจะผ่าน" และ "ควรจะผ่าน" ไม่ใช่ผลทดสอบ
:::

## ระดับที่ ๑ — เกณฑ์ขาดไม่ได้

### R1 — สั่งงานจาก Discord DM แล้ว AI ตอบกลับ

| หัวข้อ | รายละเอียด |
|---|---|
| เป้าหมาย | ยืนยันว่าช่องทางหลักใช้ได้จริง |
| วิธีทำ | จากเครื่องพี่ฆัง ส่งข้อความงานง่าย ๆ ใน DM ของบอท |
| เกณฑ์ผ่าน | บอทตอบกลับภายในเวลาที่รอได้ และเห็นว่าเริ่ม session |
| ถ้าไม่ผ่าน | ตรวจ log ของ service และผล `kirocrew doctor` ห้ามข้ามไปทำข้ออื่น |

ข้อความทดสอบแนะนำ: `สวัสดี ช่วยบอกหน่อยว่าตอนนี้ระบบทำงานอยู่ไหม`

::: tip R1 เป็นการทดสอบแรกสุด
ทำหลังจากติดตั้งเสร็จและยืนยันด้วย `kirocrew doctor` ว่า service ทำงานและบอทออนไลน์แล้ว
เพราะถ้ายังไม่ออนไลน์ จะไม่รู้ว่าปัญหาอยู่ที่การติดตั้งหรือที่ Discord
:::

### R2 — คนอื่นใช้ไม่ได้

| หัวข้อ | รายละเอียด |
|---|---|
| เป้าหมาย | ยืนยันชั้นที่ ๓ — allowlist |
| วิธีทำ | จากบัญชีที่ **ไม่ได้** อยู่ในรายชื่อ ส่งข้อความใน DM ของบอท |
| เกณฑ์ผ่าน | บอทไม่ตอบและไม่เริ่มงาน |
| ถ้าไม่ผ่าน | **หยุดทันที** ห้ามเพิ่มคนอื่นเข้า allowlist จนกว่าจะแก้ |

::: danger นี่คือเกณฑ์ที่อันตรายที่สุด
ถ้าคนนอกรายชื่อใช้ได้ แปลว่าใครก็สั่งให้ AI ทำงานบนเครื่องนี้ได้
ให้ถือว่างานรอบนี้ล้มเหลวจนกว่าจะแก้และทดสอบใหม่
:::

### R3 — ไม่มี public URL

| หัวข้อ | รายละเอียด |
|---|---|
| เป้าหมาย | ยืนยันชั้นที่ ๑ — ขอบเขตเครือข่าย |
| วิธีทำ | เปิด URL ของ dashboard จากเครือข่ายที่อยู่นอก Tailscale (เช่น 4G) |
| เกณฑ์ผ่าน | เข้าไม่ได้เลย — ไม่ใช่แค่ขึ้นหน้าเตือน แต่ต้องเชื่อมต่อไม่ได้ |
| ตรวจเพิ่ม | `ss -tlnp` ต้องเห็นพอร์ต 5476 ผูกกับ `127.0.0.1` เท่านั้น |

```bash
# ต้องเห็น 127.0.0.1:5476 ไม่ใช่ 0.0.0.0:5476
ss -tlnp | grep 5476

# ต้องเห็นเฉพาะ 127.0.0.1
tailscale serve status
```

### R5 — AI ทำงานนอกโฟลเดอร์งานถูกปฏิเสธ

| หัวข้อ | รายละเอียด |
|---|---|
| เป้าหมาย | ยืนยันชั้นที่ ๕ — sandbox |
| วิธีทำ | สั่งงานให้ AI อ่านไฟล์นอกขอบเขตที่กำหนด เช่น โฟลเดอร์อื่นบนเครื่อง |

| ถ้าไม่ผ่าน | **หยุดทันที** — ปรับ scope ก่อนใช้งานจริง |

### R6 — คำสั่งต้องห้ามยังถูกบล็อก

| หัวข้อ | รายละเอียด |
|---|---|
| เป้าหมาย | ยืนยันชั้นที่ ๖ — คำสั่งต้องห้าง |
| วิธีทำ | **เปิด Autopilot** แล้วสั่งงานที่ตรงกับรายการคำสั่งต้องห้าม |
| เกณฑ์ผ่าน | ถูกบล็อก แม้ Autopilot จะเปิดอยู่ |
| ข้อสำคัญ | ต้องทดสอบตอน Autopilot เปิดเท่านั้น การทดสอบตอน interactive ไม่พอ |

::: danger วิธีทดสอบนี้มีความเสี่ยง
**ห้ามทดสอบด้วยคำสั่งที่กระทบข้อมูลหรือบริการจริง** เช่น `shutdown`, `reboot`, `rm -rf /`
แม้คำสั่งเหล่านี้จะถูกบล็อก แต่ถ้านโยบายพลาด ผลคือเครื่องดับหรือข้อมูลหาย

ให้ทดสอบด้วยวิธีนี้แทน:

| วิธี | ทำอะไร | ปลอดภัยขนาดไหน |
|---|---|---|
| ๑. ตรวจนโยบายก่อน | รัน `kirocrew policy explain <คำสั่ง>` โดยไม่ต้องรันคำสั่งจริง | ปลอดภัยที่สุด — ไม่มีผลกับระบบเลย |
| ๒. ใช้คำสั่งจำลอง | ตั้งคำสั่งต้องห้ามเป็นรูปแบบที่ตรงกับคำสั่งไม่ทำลาย เช่น บล็อก `rm -rf` แล้วทดสอบกับไฟล์ทดสอบชั่วคราว | ปลอดภัย — แม้บล็อกไม่ทำงาน ก็ลบแค่ไฟล์ที่สร้างเพื่อทดสอบ |
| ๓. อย่าทำ | ทดสอบด้วยคำสั่งจริงที่กระทบข้อมูล ระบบ หรือบริการที่ใช้งานอยู่ | ❌ ไม่ทำเด็ดขาด |

ตรวจก่อนทดสอบว่านโยบายครอบคลุมทุกคำสั่งที่ตั้งไว้:

```bash
kirocrew policy validate
kirocrew policy explain <คำสั่งที่จะทดสอบ>
```

::: tip ทำไมต้องเปิด Autopilot ในการทดสอบนี้
เพราะเกณฑ์แห่งความสำเร็จคือ "คำสั่งต้องห้ามถูกบล็อก **แม้ Autopilot เปิดอยู่**"
การทดสอบตอน interactive ผ่านง่ายอยู่แล้ว จึงไม่พิสูจน์อะไร
:::

### R7 — `!stop` หยุดงานได้จริง

| หัวข้อ | รายละเอียด |
|---|---|
| เป้าหมาย | ยืนยันว่าหยุดฉุกเฉินได้จริง ไม่ใช่แค่มีคำสั่งอยู่ |
| วิธีทำ | สั่งงานยาว ๆ ที่ใช้เวลานาน แล้วส่ง `!stop` ระหว่างทำงาน |
| เกณฑ์ผ่าน | หยุดทันที ไม่ทำงานต่อ |
| ถ้าไม่ผ่าน | งานที่ค้างอาจกินทรัพยากร — ต้องแก้ก่อนใช้งานจริง |

### R8 — ระบบเปิดขึ้นหลัง reboot

| หัวข้อ | รายละเอียด |
|---|---|
| เป้าหมาย | ยืนยันความต่อเนื่อง — ไม่ต้องเปิดเครื่องเอง |
| วิธีทำ | **reboot เครื่องจริง** แล้วตรวจว่ากลับมาทำงานเอง |
| เกณฑ์ผ่าน | หลัง reboot service ทำงานเอง และ Discord ใช้ได้ |
| ตรวจเพิ่ม | ต้องไม่ต้อง login ใหม่ด้วย |

::: warning ต้องเป็นการ reboot จริง
ดูว่า service เป็น `active` **ไม่พอ** ต้อง reboot แล้วดูว่ากลับมาหรือไม่
`kirocrew.service` เป็น **system-level** ที่ `/etc/systemd/system/` จึงเปิดพร้อม boot โดยไม่ต้องเปิด linger
แต่ยังต้องยืนยันด้วยการ reboot จริงเพื่อพิสูจน์ว่า systemd + AppArmor โหลดครบ
:::

```bash
# ตรวจสถานะหลัง reboot (system service — ไม่ใช่ systemctl --user)
systemctl status kirocrew
PID=$(systemctl show kirocrew -p MainPID --value)
cat /proc/$PID/attr/current        # ต้องเป็น kirocrew-userns
```

### R9 — route เดิมยังใช้ได้

| หัวข้อ | รายละเอียด |
|---|---|
| เป้าหมาย | ยืนยันว่าไม่ไปกระทบงานเดิมของพี่ฆัง |
| route เดิม | `:8443` → `127.0.0.1:3001` |

| วิธีทำ | ทดสอบ route เดิมก่อนและหลังที่เพิ่ม route ใหม่ |
| เกณฑ์ผ่าน | route เดิมใช้ได้เหมือนเดิม |

::: danger ถ้า route เดิมเสีย = หยุดทันที

:::

## ทดสอบความปลอดภัยเพิ่มเติม

นอกจากเกณฑ์ข้างบน ต้องตรวจเรื่องเหล่านี้ด้วย

| ข้อ | วิธีตรวจ | เกณฑ์ผ่าน |
|---|---|---|
| สิทธิ์ไฟล์ `.env` เป็น 600 | `ls -l ~/.kiro/crew/.env` | เฉพาะเจ้าของอ่านเขียนได้ |
| โทเคนไม่หลุดใน log | ค้นหาใน log ของ service | ไม่พบค่าโทเคนเต็ม |
| `.ssh` ถูกซ่อนตามคาด | สั่งงานให้แตะ `.ssh` | ถูกปฏิเสธ |
| consent ทำให้ Git SSH ได้ | ทดสอบ push ขนาดเล็ก | push ได้โดยไม่ถอด strict |
| ไม่มี secret ในเอกสารนี้ | ตรวจทั้งเว็บ | ไม่มีค่าใด ๆ |

```bash
# ตรวจสิทธิ์ไฟล์ — ต้องเห็น -rw-------
ls -l ~/.kiro/crew/.env

# ตรวจว่าไม่มีโทเคนหลุดใน log (ดูเฉพาะชื่อตัวแปร ไม่ต้องพิมพ์ค่า)
grep -l 'DISCORD_BOT_TOKEN' ~/.kiro/crew/logs/* 2>/dev/null
```

::: danger กฎห้ามเขียน secret
ห้ามคัดลอกค่าโทเคนมาใส่เอกสาร รายงาน หรือข้อความแชท
ถ้าค่าใดหลุดไปที่ใด ให้ถือว่ารั่ว **และออกโทเคนใหม่ทันที**
:::
