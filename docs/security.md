# ๖. ความปลอดภัย

หน้านี้อธิบายว่า **ระบบถูกคุมอย่างไร** — เป็นหน้าที่พี่ฆังต้องอ่านก่อนอนุมัติให้ติดตั้ง

::: danger หลักการเดียวของหน้านี้
ระบบนี้ให้ AI ทำงานกับไฟล์จริงบนเครื่องจริง ทุกช่องทางเข้าต้องแคบ
และทุกการกระทำที่มีผลต้องมีจุดที่พี่ฆังเห็นและอนุมัติได้
:::

## ภาพรวมชั้นการป้องกัน

```
┌─────────────────────────────────────────────┐
│  ๑. ขอบเขตเครือข่าย — Tailscale เท่านั้น     │
├─────────────────────────────────────────────┤
│  ๒. การยืนยันตัวตน — โทเคนบังคับทุกคำขอ     │
├─────────────────────────────────────────────┤
│  ๓. การยอมรับคนสั่ง — allowlist เท่านั้น     │
├─────────────────────────────────────────────┤
│  ๔. การอนุมัติ — เราตั้งเป็น interactive    │
├─────────────────────────────────────────────┤
│  ๕. ขอบเขตไฟล์ — sandbox strict             │
├─────────────────────────────────────────────┤
│  ๖. คำสั่งต้องห้าง — บังคับใช้ ไม่มีข้อยกเว้น │
├─────────────────────────────────────────────┤
│  ๗. ซ่อนข้อมูลอ่อนไหว + บันทึกตรวจสอบย้อนหลัง │
└─────────────────────────────────────────────┘
```

ชั้นใดชั้นหนึ่งพัง = ระบบไม่ปลอดภัย ต้องแก้ก่อนใช้งานจริง

---

## ๑. ขอบเขตเครือข่าย — ไม่มีทางเข้าจากอินเทอร์เน็ตสาธารณะ

### หลักการ

| หัวข้อ | ค่าที่ตั้ง | เหตุผล |
|---|---|---|
| ที่ฟังจริง | `127.0.0.1:5476` | ผูกเฉพาะ loopback — ไม่รับการเชื่อมต่อจากเครือข่ายใดได้เลย |
| ทางเข้าจากภายนอก | `kirocrew tailnet up` เท่านั้น | Crew จัดการ trust/ACL/cert เอง · เฉพาะอุปกรฑ์ใน tailnet · ห้ามแก้ `tailscale serve` เอง |
| ผนังกั้นเพลิงระดับระบบ | ไม่ได้ติดตั้ง | ไม่ใช้ชั้นนี้เป็นการป้องกัน — พึ่ง Tailscale เป็นชั้นเดียว |

::: warning ไม่มีผนังกั้นเพลิง
ตรวจแล้วไม่พบ `ufw`/`firewalld` บนเครื่อง ระบบจึงพึ่ง Tailscale + loopback binding เป็นการป้องกันจริง
ถ้าวันหนึ่งตั้งผนังกั้นเพลิง ต้องเปิดพอร์ตให้ Tailscale ด้วย ไม่ใช่ปิดทั้งหมด
:::

### การเข้าถึงจากภายนอกทดสอบอย่างไร

ต้องทดสอบว่า **เข้าไม่ได้** จากเครือข่ายนอก Tailscale — ดูรายละเอียดใน [๗. การทดสอบ](/testing) (R3)

## ๒. การยืนยันตัวตน — โทเคนบังคับทุกคำขอ

| หัวข้อ | ค่า |
|---|---|
| วิธียืนยัน | Bearer token ทุกคำขอ |
| เก็บโทเคน | `~/.kiro/crew/.env` สิทธิ์ไฟล์ `600` |
| อายุโทเคน | 20 ชั่วโมง |
| ผู้ถือโทเคน | พี่ฆังเท่านั้น |

```bash
# สร้างโทเคนเข้า dashboard
kirocrew token --ttl 20h
```

::: tip เหตุผลที่ตั้งอายุโทเคนสั้น
โทเคนที่อยู่ตลอดไปคือความเสี่ยงที่ไม่มีวันหมดอายุ การตั้ง 20 ชั่วโมงทำให้กรณีหลุดรั่วอย่างไร
ต้องรอให้หมดอายุเอง หรือออกใหม่เมื่อสงสัยว่ามีใครได้ไปแล้ว
:::

### กฎข้อ ๑ ของครอบครัว — ห้ามเขียนโทเคนลงที่ใด

| ❌ ห้าม | ✅ ต้อง |
|---|---|
| เขียนโทเคนในโค้ด | อ่านจาก `.env` เท่านั้น |
| เขียนโทเคนในเอกสารนี้ | อ้างอิงเป็นตำแหน่งไฟล์ |
| พิมพ์โทเคนลงคำสั่ง bash | ใช้วิธีที่ไม่บันทึกลงประวัติ |
| ส่งโทเคนเข้าแชท Discord | ใส่ `.env` ผ่านช่องทางที่กำหนด |

เหตุผล: คำสั่ง bash ทุกคำสั่งถูกบันทึกใน `opencode.log` โทเคนที่หลุดลงไปต้องถือว่ารั่วและต้องออกใหม่ทันที

## ๓. การยอมรับคนสั่งงาน — allowlist เท่านั้น

| หัวข้อ | ค่า |
|---|---|
| หลักการ | ปฏิเสธเป็นค่าเริ่มต้น (deny by default) |
| รายชื่อที่อนุญาต | `discord.allowed_user_ids` ใน `~/.kiro/crew/config.json` |
| เริ่มต้น | พี่ฆังคนเดียว |
| ช่องทางเริ่มแรก | DM เท่านั้น |

### ทำไมเริ่มจาก DM และคนเดียว

- ชัดเจนว่าใครสั่งอะไร — แยก session ต่อคน
- ไม่มีข้อความปนกวนจากคนอื่นในห้อง
- เหมาะกับงานที่ต้องอนุมัติ เพราะจุดอนุมัติไม่ถูกแย่งกด

::: danger ห้ามขยาย allowlist จนกว่าจะทดสอบผ่าน
ต้องพิสูจน์ก่อนว่า **คนที่ไม่อยู่ในรายชื่อใช้ไม่ได้จริง** (R2) ไม่ใช่แค่ตั้งค่าไว้แล้วเชื่อว่าทำงาน
:::

## ๔. การอนุมัติ — interactive เป็นค่าที่เราตั้งเอง ไม่ใช่ค่าเริ่มต้นของระบบ

| โหมด | การใช้งาน | สถานะบน sv |
|---|---|---|
| `interactive` | ทุกการกระทำที่มีผลต้องรออนุมัติ | **ค่าที่เราตั้งตามแผนนี้** — ยังไม่ได้ตั้งจริง |
| `auto` | ทำงานที่มีผลได้เอง | ⚠️ **ค่าเริ่มต้นจริงของ Crew 0.7.2** ที่ยังใช้อยู่ตอนนี้ |
| Autopilot | ทำงานต่อเนื่องเอง | เปิดต่อ session เท่านั้น ไม่เปิดเป็นค่าถาวร |

::: danger ตรวจจริงแล้ว: ค่าเริ่มต้นคือ `auto`
`kirocrew doctor` บน sv รายงาน `approval: auto`
ค่านี้มาจาก `defaults.json` ที่ติดมากับ Crew — เอกสารเดิมเขียนว่า `interactive` เป็นค่าเริ่มต้น ซึ่งผิด

ถ้าเปิดใช้งานจริงตอนนี้โดยยังไม่แก้ **งานที่มีผลกับระบบจะทำได้โดยไม่ต้องรอคนอนุมัติ**
ต้องตั้ง `agent.approval_mode = interactive` ก่อนเปิดใช้งานจริงเสมอ
:::

### ใครอนุมัติได้

พี่ฆังเท่านั้น — กด Approve/Reject ในแชท Discord หรือใน dashboard

::: warning Autopilot ไม่ใช่ทางออกของความขี้เกียจ
Autopilot ข้ามได้เฉพาะ**จุดอนุมัติ** เท่านั้น — คำสั่งต้องห้ามและขอบเขต sandbox ยังบังคับใช้เสมอ
เปิด Autopilot แล้วคำสั่งต้องห้ามยังถูกบล็อก (R6)
:::

## ๕. ขอบเขตไฟล์ — sandbox strict

| ค่า | ระดับ | ผล |
|---|---|---|
| `agent.sandbox` | `strict` | จำกัดการเข้าถึงให้แคบที่สุด — ตั้งเองไม่ได้ ต้องให้เครื่องรองรับ |

::: info ค่า `strict` เป็นเป้าหมาย ไม่ใช่ค่าที่ตั้งไว้แล้ว
อ่านค่าจริงได้ด้วย `kirocrew config get agent.sandbox` → ตอนนี้ได้ `auto`
`auto` จะเลือก strict เองเมื่อ probe ผ่าน แต่ probe ของ `sv` ล้มเหลว เพราะ
`kernel.apparmor_restrict_unprivileged_userns = 1` ต้องติดตั้ง profile ก่อน
:::

### สิ่งที่ sandbox strict อาจซ่อน

| โฟลเดอร์ | ทำไมถึงซ่อน | วิธีจัดการ |
|---|---|---|
| `.ssh` | เป็นคีย์เข้าถึงเครื่องอื่น | consent ไฟล์เฉพาะ ไม่ถอด strict |
| `.aws` | เป็นข้อมูลรับรอง | ยังไม่ต้องใช้ — ถ้าต้องใช้ค่อยขอ |
| `.kube` | เป็นคีย์ควบคุมคลัสเตอร์ | ยังไม่ใช้ |
| `.gnupg` | เป็นคีย์เข้ารหัส | ยังไม่ใช้ |

### กรณี Git SSH ต้องใช้

เมื่อต้อง push โค้ดขึ้น Gitea ผ่าน SSH แต่ strict ซ่อน `.ssh` — ใช้ไฟล์ consent:

```
~/.kiro/crew/ssh_auth_sock_consent.json
```

::: danger ห้ามทางลัด
ถ้า push ไม่ได้ **ห้ามถอดเป็นโหมดกว้าง** เพื่อให้ทำงานผ่าน
ต้องแก้ที่ consent แล้วทดสอบซ้ำ — เพราะการถอด strict ทำให้เสียชั้นป้องกันข้อ ๕ ทั้งชั้น
:::

## ๖. คำสั่งต้องห้าม — บังคับใช้ ไม่มีข้อยกเว้น

| คำสั่ง | เหตุผล |
|---|---|
| ลบไฟล์ทั้งระบบ | ไม่มีทางกู้คืน |
| ดันโค้ดขึ้นสาขาหลัก | กฎเด็ดขาดของครอบครัว |
| ลบตารางฐานข้อมูล | ข้อมูลหายถาวร |
| อ่านกุญแจ SSH | เป็นคีย์เข้าถึงเครื่องอื่น |
| ปิดระบบ / รีบูต | กระทบงานอื่น |

### ตรวจสอบนโยบายก่อนใช้จริง

```bash
kirocrew policy validate            # ตรวจว่านโยบายถูกต้อง
kirocrew policy show                # ดูนโยบายทั้งหมด
kirocrew policy explain <คำสั่ง>   # ถามว่าคำสั่งนี้จะถูกอนุญาตไหม
```

::: tip จุดหยุดบังคับ
รายการคำสั่งต้องห้างนี้ต้องให้พี่ฆังตรวจและอนุมัติก่อนเชื่อม Discord
เพราะเป็นกฎที่คำสั่งใด ๆ ข้ามไม่ได้ — แก้ทีหลังเท่ากับไม่มีผล
:::

## ๗. ซ่อนข้อมูลอ่อนไหวและบันทึกตรวจสอบ

| ความสามารถ | ทำอะไร |
|---|---|
| ปิดบังข้อมูลอ่อนไหวในผลลัพธ์ | ไม่ให้โทเคน/รหัสผ่านหลุดออกมาทางข้อความตอบ |
| บันทึกเหตุการณ์ความปลอดภัย | บันทึกการเข้าถึงที่ถูกปฏิเสธ และการกระทำที่ผ่าน |
| ตรวจสอบย้อนหลังได้ | เปิดดูว่าใครสั่งอะไร เมื่อไร ได้ผลอะไร |

### ตรวจบันทึกได้ที่ไหน

| ต้องการดู | ไปที่ |
|---|---|
| ประวัติ session | หน้า Sessions ใน dashboard |
| เหตุการณ์ความปลอดภัย | หน้า Security/Audit ใน dashboard |
| ทรัพยากรที่ใช้ | หน้า System |

::: warning บันทึกเก็บไว้ที่ `~/.kiro/crew/`
เป็นข้อมูลของระบบ — ถ้าจะสำรองหรือย้ายเครื่อง ต้องระวังว่าบันทึกอาจมีเนื้อหาของงานจริงปนอยู่
:::

## ชั้นควบคุมสองชั้น

นโยบายถูกอ่านจากสองแหล่ง และ **ผลที่บังคับใช้คือสิ่งที่ทั้งสองชั้นอนุญาตร่วมกัน**

```
เพดานสูงสุด   security_policy.json     ← ห้ามเกินนี้เด็ดขาด
      ↓
กรองเฉพาะงาน  profiles/                ← เข้มงวดยิ่งได้
      ↓
ผลที่บังคับใช้  = สิ่งที่ทั้งสองชั้นอนุญาตร่วมกัน
```

| กรณี | เพดานสูงสุด | profile | ผล |
|---|---|---|---|
| อ่านไฟล์ในโฟลเดอร์งาน | อนุญาต | อนุญาต | ✅ อนุญาต |
| เขียนนอกโฟลเดอร์งาน | อนุญาต | ห้าม | ❌ ห้าม |
| คำสั่งต้องห้าง | ห้าม | อนุญาต | ❌ ห้าม |

::: tip เข้มงวดที่สุดเป็นผล
งานที่อยากให้ทำเองได้ ต้องเพิ่มความยอมให้**ทั้งสองชั้นพร้อมกัน** — แก้ชั้นเดียวไม่มีผล
:::

## ตารางสรุปความเสี่ยงที่รับไว้

| ความเสี่ยง | ระดับ | เหตุผลที่รับไว้ |
|---|---|---|
| ผู้ใช้ใน allowlist สั่งงานผิด | ปานกลาง | มีจุดอนุมัติ + ประวัติ + ย้อนหลังได้ |
| โทเคน dashboard หลุด | ต่ำ | อายุ 20 ชม · loopback · Tailscale · ถ้าหลุดให้ออกใหม่ทันที |
| `agy`/Copilot ทำงานนอกขอบเขต | สูง | ❌ **ไม่รับ** — ยังไม่เชื่อม จนกว่าจะมีช่องทางที่คุมได้ |
| AI ใช้ทรัพยากรจนเต็ม | ต่ำ | RAM ว่าง 25 GiB · ดิสก์ว่าง 51 GB + เห็นสถานะสดใน dashboard |
| ถ้าใครขอสิทธิ์ผ่าน SSH | ต่ำ | ไม่มีช่องทางที่เปิดให้ใช้ · ตรวจจาก audit ได้ |

::: danger ความเสี่ยงที่ไม่รับ
- เปิดสู่สาธารณะ
- คนนอก allowlist สั่งงานได้
- คำสั่งต้องห้ามถูกข้าม
- โทเคนอยู่ในโค้ดหรือเอกสาร

ถ้าเกิดข้อใดข้อหนึ่ง ถือว่างานรอบนี้ล้มเหลวทันที ไม่ต้องดูเกณฑ์อื่น
:::

## สิ่งที่ยังไม่ได้ทดสอบเรื่องความปลอดภัย

| ข้อ | ทำไมสำคัญ | ถ้าไม่ผ่าน |
|---|---|---|
| การเข้าถึงจากนอก Tailscale ต้องถูกปิด (R3) | ยืนยันชั้นที่ ๑ | เปลี่ยนวิธีเข้าถึงทั้งหมด |
| คนนอก allowlist ใช้ไม่ได้ (R2) | ยืนยันชั้นที่ ๓ | หยุดแก้ทันที ห้ามเพิ่มคนอื่น |
| Dashboard ปฏิเสธเมื่อไม่มีโทเคน (R4) | ยืนยันชั้นที่ ๒ | ห้ามเปิดใช้งานจริง |
| Sandbox บล็อกการออกนอกโฟลเดอร์งาน (R5) | ยืนยันชั้นที่ ๕ | ปรับ scope หรือหยุด |
| Autopilot ไม่ข้ามคำสั่งต้องห้าม (R6) | ยืนยันชั้นที่ ๖ | ปิด Autopilot ทันที |
| การส่งต่อ SSH ผ่าน consent | กระทบการ push โค้ด | ต้องตั้ง consent ก่อน |
| route เดิม `:8443` ไม่เสีย | กระทบงานเดิม | หยุดแก้ทันที |

## กฎเหล็กที่ต้องจำ

1. **ไม่มี public URL** — เข้าถึงได้ทางเดียวคือ Tailscale
2. **ไม่มีโทเคน = ไม่มีการเข้าถึง** — ไม่มีทางเลี่ยน
3. **คนที่ไม่อยู่ในรายชื่อ = ใช้ไม่ได้** — ปฏิเสธเป็นค่าเริ่มต้น
4. **ทำงานที่มีผล ต้องอนุมัติก่อน** — ตั้ง `interactive` เอง (ค่าเริ่มต้นของระบบคือ `auto`)
5. **คำสั่งต้องห้าม ข้ามไม่ได้** — ไม่มีข้อยกเว้น ไม่มี Autopilot
6. **โทเคนไม่มีที่ไหนนอก `.env`** — และถ้าหลุดให้ถือว่ารั่ว ต้องออกใหม่
7. **ห้ามถอด strict เพื่อให้งานผ่าน** — แก้ที่ consent แทน
