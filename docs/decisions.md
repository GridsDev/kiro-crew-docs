# ภาคผนวก ก — บันทึกการตัดสินใจ

บันทึกไว้เพื่อไม่ให้ต้องถามซ้ำว่า "ทำไมถึงเลือกแบบนี้" และเพื่อให้คนใหม่ในทีมเข้าใจโดยไม่ต้องย้อนประวัติแชท

::: info วิธีอ่านหน้านี้
แต่ละรายการบอกว่า **ตัดสินใจอะไร** · **ทำไม** · **ยังมีอะไรไม่รู้**
รายการที่ยังไม่ได้ตัดสินใจจะอยู่ในหัวข้อสุดท้าย ไม่ปนกับของที่เสร็จแล้ว
:::

---

## ๑ — รันบนเครื่อง `sv`

| | |
|---|---|
| **ตัดสินใจ** | ระบบทั้งหมดทำงานบน Ubuntu Server เครื่อง `sv` ไม่ใช่คอมพิวเตอร์ตั้งโต๊ะ |
| **ทำไม** | เครื่องนั้นเปิดอยู่ตลอด ไม่ต้องพึ่งการเปิดเครื่องคอมพิวเตอร์ · มี Tailscale อยู่แล้ว · ทรัพยากรพอ (RAM ว่าง 25 GiB · ดิสก์ว่าง 51 GB) |
| **ยังไม่รู้** | — ข้อมูลนี้ตรวจจริงแล้ว |

| | |
|---|---|
| **ตัดสินใจ** | Dashboard ฟังที่ `127.0.0.1:5476` เท่านั้น และต้องมี token |
| **ทำไม** | ไม่มีการยืนยันตัวตน = ใครก็เข้าถึงได้ทั้งเครื่อง · token ทำให้ทุกครั้งที่เข้าต้องยืนยัน |
| **รายละเอียด** | token มีอายุประมาณ ๒๐ ชั่วโมง แล้วต้องขอใหม่ |
| **ยังไม่รู้** | ยังไม่ทดสอบว่าการเข้าผ่าน Tailscale จะทำให้ token ต้องขอใหม่บ่อยขึ้นไหม |

## ๖ — ตั้ง `interactive` ให้เหนือกว่าค่าเริ่มต้น `auto` ของระบบ

| | |
|---|---|
| **ตรวจพบ** | ค่าเริ่มต้นจริงของ Crew 0.7.2 คือ `auto` ไม่ใช่ `interactive` (ยืนยันจาก `kirocrew doctor` บน sv) |
| **ตัดสินใจ** | ตั้ง `agent.approval_mode = interactive` เพื่อให้ตรงกับแผนนี้ |
| **ทำไม** | พี่ฆังเป็นคนเดียวที่สั่งได้ งานส่วนใหม่เป็นงานที่แก้ไฟล์และรันคำสั่งบนเครื่องจริง ความปลอดภัยสำคัญกว่าความเร็ว · และเพราะค่าเริ่มต้น `auto` จะทำงานที่มีผลได้โดยไม่รออนุมัติ ซึ่งต่างจากที่ตกลงกัน |
| **ต้นทุนของการเลือกแบบนี้** | ต้องกดอนุมัติทุกครั้ง · งานอัตโนมัติที่ไม่มีคนอยู่จะใช้เครื่องมือไม่ได้ |
| **สถานะ** | ⏳ ยังไม่ได้ตั้ง — `config.json` ยังไม่มีค่านี้ ระบบยังใช้ `auto` อยู่ |
| **ยังไม่รู้** | จะเป็นปัญหามากไปหรือไม่ในการใช้งานจริง — ต้องทดสอบแล้วประเมินใหม่ |

::: warning ยอมรับข้อจำกัดนี้ไว้ก่อน
งานที่รันอัตโนมัติโบกุ้งไว้จะไม่ทำงานในโหมดนี้
ถ้าตอนใช้จริงพบว่าเป็นปัญหามาก ทางแก้คือเปลี่ยนช่องทางทำงานเครื่องมือหนักไปที่ dashboard
**ไม่ใช่** การเปิด `auto` ทั้งระบบ
:::

## ๗ — นโยบายสองชั้น: กว้าง + แคบ

| | |
|---|---|
| **ตัดสินใจ** | มีทั้ง `security_policy.json` (เพดานสูงสุด) และ `profiles/` (เฉพาะงาน) |
| **ทำไม** | ชั้นเดียวไม่พอ — ถ้ากว้างอย่างเดียวก็กว้างเกินไป ถ้าแคบอย่างเดียวก็งานใหม่จะทำอะไรไม่ได้เลย |
| **หลักการ** | ผลลัพธ์จริง = สิ่งที่ **ทั้งสองชั้นอนุญาตร่วมกัน** · ไม่อยู่ในรายการ = ปฏิเสธ ไม่ใช่ "อนุญาต" |
| **ยังไม่รู้** | ยังไม่ได้เขียนนโยบายจริง — รอตอนมีกรณีใช้งานจริง |

## ๘ — ให้ sandbox ทำงานแบบ strict ผ่าน profile ทางการ แก้ที่ consent

| | |
|---|---|
| **ตัดสินใจ** | ใช้ sandbox แบบ strict โดยติดตั้ง AppArmor profile ด้วยคำสั่งทางการของ Crew และใช้ consent file สำหรับ Git SSH |
| **ทำไม** | strict ปิดคำสั่งนอกขอบเขตโดยไม่ถาม ซึ่งเป็นการป้องกันจริง · การถอด sandbox เพื่อให้ Git ทำงานแปลว่าเอากำแพงทั้งหมดออกเพื่อแก้ประตูหน้าเดียว |
| **รายละเอียด** | คำสั่งทางการสำหรับเครื่องที่ไม่ใช่ AppImage คือ `kirocrew service install` (sudo) และทางเลือกคือ `kirocrew sandbox install-profile --path /home/devg/.local/bin/kirocrew` (sudo) · เครื่องนี้มี `kernel.apparmor_restrict_unprivileged_userns = 1` จึงจำเป็นตามเอกสารของ Crew เอง · consent สำหรับ Git SSH ยังไม่ได้สร้าง |
| **สถานะจริง** | ✅ **ทำแล้ว 3 ต.ค. 2569** — `kirocrew service install` ติดตั้ง AppArmor profile สำเร็จ · `unshare -U true` ผ่าน · `SandboxUnavailableError` = 0 หลังติดตั้ง · `agent.sandbox` ยังคงเป็นค่าเริ่มต้น `auto` (ซึ่งเลือก strict ให้เองเพราะเครื่องรองรับแล้ว) |
| **ขั้นตอนที่ทำก่อน** | ลดสิทธิ์ `/home/devg/.kiro` จาก `775` เป็น `750` — Crew ปฏิเสธ profile เพราะกลุ่มมีสิทธิ์เขียน · ตรวจ `getent group devg` ก่อนทุกครั้ง — ✅ **ทำแล้ว** |
| **ทางเลือกที่ไม่ได้ใช้** | `kirocrew sandbox install-profile --path ...` — ไม่จำเป็นแล้ว เพราะ `service install` แก้ได้ครบในคำสั่งเดียว · ไม่ได้รัน และพี่ฆังอนุมัติเฉพาะทาง `service install` เท่านั้น |
| **ยังไม่รู้** | ยังไม่ทดสอบว่า Git SSH ทำงานได้จริงภายใต้เงื่อนไขนี้ · ยังไม่ทดสอบ agent ทำงานจริง end-to-end |

## ๙ — ให้ Crew จัดการ service เอง แทนการเขียน unit เอง

| | |
|---|---|
| **เดิม** | ตัดสินใจเป็น service ระดับผู้ใช้ ที่ `~/.config/systemd/user/kirocrew.service` — เพราะคิดว่าจะได้ไม่ต้องใช้สิทธิ์ root |
| **ตรวจพบจริง** | `kirocrew service install` สร้าง **system-level** ที่ `/etc/systemd/system/kirocrew.service` · ยืนยันแล้วว่า `/home/devg/.config/systemd/user/` ไม่มีอยู่ และ `sv-opencode-serve.service` เดิมเป็น system-level ที่ `/etc/systemd/system/` — **ไม่ชนกัน** |
| **ตัดสินใจ** | ใช้ทางที่ Crew จัดการเอง ไม่เขียน unit เอง |
| **ทำไม** | คำสั่งเดียวได้ทั้ง systemd unit **และ** AppArmor profile พร้อมกัน — เขียนเองจะได้แค่ service แล้วต้องแก้ sandbox อีกทาง |
| **ผลกระทบที่ต่างจากแผน** | ต้องใช้ sudo ตอนติดตั้ง (ผ่าน `~/python-tools/sv.py` ตามช่องทางที่พี่ฆังกำหนด) · เรียกด้วย `systemctl` ไม่ใช่ `systemctl --user` · **ไม่ต้องเปิด linger** |
| **สถานะจริง** | ✅ `enabled` / `active` ตั้งแต่ `Sat 2026-10-03 21:10:13 +07` · ไม่ได้รัน `loginctl enable-linger devg` |
| **ยังไม่รู้** | ยังไม่ทดสอบ **R8 — reboot จริง** ว่ากลับมาทำงานเองหรือไม่ ต้องเปิดเครื่องใหม่จริงถึงจะบันทึกว่าผ่านได้ |

## ๙.๑ — ลดสิทธิ์ `/home/devg/.kiro` เป็น `750` ก่อนติดตั้ง profile

| | |
|---|---|
| **ตัดสินใจ** | `chmod 750 /home/devg/.kiro` (เดิม `775`) โดยพี่ฆังอนุมัติ |
| **ทำไม** | Crew ปฏิเสธติดตั้ง AppArmor profile เพราะโฟลเดอร์เขียนได้โดยกลุ่ม — เปิดช่องให้ผู้ใช้อื่นในเครื่องที่ login ได้สามารถวาง executable ปลอมไว้ในตำแหน่งที่ gateway จะเรียกใช้ |
| **ตรวจก่อนลดสิทธิ์** | `getent group devg` → `devg:x:1000:` ไม่มีสมาชิกอื่น · มี login user เดียวคือ `devg` · มีแค่ `kirocrew.service` ที่อ้างถึง `~/.kiro` |
| **ผลกระทบ** | ไม่มีผู้ใช้หรือ service อื่นเสียสิทธิ์ · คำสั่งทางการของ Crew ติดตั้ง profile ผ่านทันที |
| **ข้อควรระวัง** | ต้องตรวจ group membership ก่อนลดสิทธิ์ทุกครั้ง — ถ้ามีสมาชิกกลุ่มเพิ่ม ต้องคุยพี่ฆังใหม่ ห้ามลดเอง |

## ๑๐ — ใช้ `kirocrew tailnet up` แทนการเพิ่ม Serve route เอง

| | |
|---|---|
| **เดิม** | วางแผนเพิ่ม Tailscale Serve route `:8444 → 127.0.0.1:5476` ด้วยคำสั่ง `tailscale serve` เอง |
| **ตรวจพบจริง** | Crew 0.7.2 มีคำสั่งจัดการเองคือ `kirocrew tailnet up/down/status` และ `tailnet status` รายงานว่าจะ publish บน **port 443** ไม่ใช่ 8444 (`nothing is on port 443`) |
| **ตัดสินใจ** | ใช้ `kirocrew tailnet up` เป็นทางหลัก เพราะ Crew จัดการ trust/ACL/renew ให้เอง ไม่ต้องเขียน Serve config เอง |
| **ทำไม** | ถ้าเขียน `tailscale serve` เอง เราจะเป็นคนดูแล trust origin, ACL และ cert renewal เอง และอาจชนกับสิ่งที่ Crew คาดว่าจะจัดการ |
| **ยังไม่รู้** | ยังไม่ทดสอบว่า `kirocrew tailnet up` จะกระทบ route `:8443 → 127.0.0.1:3001` ของ Billing หรือไม่ — **ต้องตรวจและทดสอบก่อน** |
| **สถานะ** | ⏳ ยังไม่เปิด — `tailnet status` ยังขึ้น `Trust: disabled` และ `Published: no` |

::: danger ห้ามเปิด tailnet โดยพลการ
`kirocrew tailnet up` เป็นการเปิดช่องทางเข้าจากภายนอก tailnet ต้องได้รับอนุมัติจากพี่ฆังก่อน
และต้องยืนยันก่อนว่า route Billing เดิมยังใช้ได้
:::

## ยังไม่ได้ตัดสินใจ

รายการนี้ยังไม่มีคำตอบ **เพราะยังไม่มีข้อมูลพอ** — ไม่ใช่เพราะลืม

| เรื่อง | ต้องมีอะไรจึงตอบได้ |
|---|---|
| จะใช้โควตากับใครบ้าง | ต้องเคยทดสอบกับคนที่สองแล้วว่าพอ |
| จะเปิดบอทเข้าเซิร์ฟเวอร์ Discord ของตัวเองไหม | ต้องชั่งกับ Message Content Intent อีกครั้งเมื่อมีเหตุผลจริง |
| จะใช้โหมด `auto` เมื่อไร | ต้องวัดก่อนว่า interactive ช้าจนรบกวนจริงหรือไม่ |
| จะเชื่อม `agy` / Copilot / LINE ได้อย่างไร | ต้องหาช่องทางที่คุมได้และกำหนดขอบเขตก่อน |
| ค่าใช้จ่ายต่อเดือนเท่าไร | ต้องตรวจบัญชีจริง |
| จะให้บอทอ่านอะไรได้นอกจากโปรเจกต์ | ต้องคุยเรื่องขอบเขตของข้อมูลก่อน |

::: tip กติกาการตัดสินใจในครอบครัวนี้
การตัดสินใจที่กระทบสิทธิ์ของเครื่อง หรือขอบเขตของข้อมูล **ต้องรอพี่ฆัง**
ฌอนเสนอได้ แต่ไม่อนุมัติแทน — และต้องบันทึกลงหน้านี้ทุกครั้งที่ตัดสินใจใหม่
:::
