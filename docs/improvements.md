# ๘. ปรับปรุงแก้ไข

หน้านี้ตอบสองคำถาม: **ตอนนี้อะไรค้างอยู่** และ **งานรอบถัดไปควรทำอะไร**

::: info สถานะ ณ วันที่ 3 ตุลาคม 2569
Kiro Crew `0.7.2` **ติดตั้งแล้ว** แต่ยังใช้งานจริงไม่ได้ — ไม่มี service, sandbox ใช้ไม่ได้, ยังไม่ได้ตั้ง approval เป็น `interactive`, ยังไม่ได้เปิด tailnet และยังไม่ได้เชื่อม Discord
หน้านี้จึงแบ่งเป็น **สิ่งที่ต้องแก้ก่อนใช้จริง** และ **งานรอบถัดไป**
:::

## ส่วนที่ ๑ — สิ่งที่ต้องแก้ก่อนใช้งานจริง

ข้อเหล่านี้ค้างอยู่และ **ต้องปิดให้ได้ก่อน** จึงจะถือว่ารอบนี้สำเร็จ
สถานะในตารางคือผลตรวจจริงบน `sv` ไม่ใช่ข้อคาดเดา

| # | เรื่อง | สถานะ | ต้องแก้อย่างไร |
|---|---|---|---|
| 1 | ความเข้ากันของ Kiro CLI 2.26.0 | ❓ ยังไม่ยืนยัน | รัน `kiro-cli acp --help` ถ้าไม่มี ต้องเขียนตัวเชื่อมแทน |
| 2 | สิทธิ์ Tailscale เขียน route | ⚠️ ยังไม่ทดสอบ | tailnet อ่านสถานะได้ (trust `disabled`) แต่ยังไม่ทดสอบเขียน ถ้าเขียนไม่ได้ต้องเปลี่ยนวิธีเข้าถึง |
| 3 | ช่องทางรหัสผ่าน sudo | ❓ ยังไม่ทดสอบ | ทดสอบโดยไม่แสดงค่า ถ้าใช้ไม่ได้ต้องหาวิธีอื่น |
| 4 | เปิดให้คงอยู่หลังออกจากระบบ | ❌ ปิดอยู่ | ต้องเปิด มิฉะนั้น R8 ไม่ผ่าน |
| 5 | โหมดสิทธิ์ที่ Crew ต้องการจาก OpenCode | ⚠️ เห็นปัญหาแล้ว | MCP projection ของ `@kirocrew-computer` หา backend package ไม่พบ |
| 6 | sandbox แบบ strict ต่อ Git SSH | ⚠️ ติดปัญหาแล้ว | ค่าจริงคือ `agent.sandbox = auto` และ probe ล้ม ต้องติด AppArmor profile ก่อน แล้วค่อยใช้ consent ถ้าจำเป็น ห้ามถอด sandbox |
| 7 | การอนุมัติผ่าน Discord | ❌ ยังไม่ได้ทำ | ต้องมีบอทและทดสอบว่าใช้งานได้จริง ไม่ใช่แค่มีปุ่ม |
| 8 | ตั้ง `approval_mode` เป็น `interactive` | ❌ ยังเป็น `auto` | ค่า default ของ Crew คือ `auto` ต้องเปลี่ยนก่อนเปิดใช้งานจริง |
| 9 | service ของ Crew | ✅ มีแล้ว | `kirocrew service install` → **system-level** ที่ `/etc/systemd/system/kirocrew.service` · `enabled` / `active` · ไม่ต้องเปิด linger |

::: danger ข้อ ๑ เป็นข้อที่เสี่ยงที่สุด
`kiro-cli --help` ไม่แสดงคำสั่ง `acp` และ `serve` แม้เอกสารทางการจะรองรับ
ต้องทดสอบตรง ๆ ก่อน — ถ้าไม่รองรับ backend ตัวแรกของแผนจะไม่ใช่ได้ ต้องเลื่อนไปตัวที่ใช้ได้จริง
:::

::: warning ข้อ ๕–๖ แก้แล้ว (3 ต.ค. 2569)
probe เคยล้มด้วย `unshare(CLONE_NEWNS) failed with errno 1 (EPERM)`
สาเหตุที่ยืนยันได้คือ `kernel.apparmor_restrict_unprivileged_userns = 1` บน `sv`
แก้แล้วโดยพี่ฆังอนุมัติ ผ่าน `~/python-tools/sv.py`:

1. ลดสิทธิ์ `/home/devg/.kiro` จาก `775` เป็น `750` — ตรวจ `getent group devg` แล้วไม่มีสมาชิกอื่นก่อน
2. รัน `kirocrew service install` (sudo) — ได้ systemd unit **และ** AppArmor profile ในคำสั่งเดียว

ผลหลังแก้: `unshare -U true` ผ่าน · `SandboxUnavailableError` = 0 · process gateway อยู่ใต้ `kirocrew-userns`
**ยังต้องพิสูจน์ต่อ:** sandbox ทำงานแล้ว แต่ยังไม่ได้พิสูจน์ว่าคุ้มครองจริงในงานจริง (รอ R1–R13)
:::

## ส่วนที่ ๒ — งานรอบถัดไป

เรียงตามความคุ้มค่า ไม่ใช่ตามความยาก

### ๑. เพิ่ม `agy` เป็น backend — R14

| หัวข้อ | รายละเอียด |
|---|---|
| เหตุผลที่ทำ | ได้ AI อีกตัวที่ตอบแทนกันได้ เพิ่มความหลากหลาย |
| สิ่งที่ต้องทำ | เขียนตัวเชื่อมให้เข้ากับ Crew เพราะยังไม่มี adapter ในตัว |
| สิ่งที่ตรวจแล้ว | `agy` รับ/ส่ง stream-json ได้ (หนึ่ง turn ต่อบรรทัด) |
| ความยาก | ปานกลาง — มีโปรโตคอลให้ใช้แล้ว แต่ต้องแปลงรูปแบบให้เข้ากัน |
| เงื่อนไข | ต้องมีโปรโตคอลที่คุมการสั่งงานได้ ไม่ใช่แค่ส่งข้อความ |

### ๒. เพิ่ม Copilot เป็น backend — R15

| หัวข้อ | รายละเอียด |
|---|---|
| เหตุผลที่ทำ | ได้อีกตัวหนึ่งในกลุ่มครอบครัว |
| สิ่งที่ต้องทำ | หา **ช่องทางผลลัพธ์แบบอ่านด้วยเครื่อง** ก่อน — ยังไม่พบ |
| สิ่งที่ตรวจแล้ว | มีตัวเลือก `-p` และ `-r` ให้สั่งงานได้ แต่ยังไม่ยืนยันว่าผลลัพธ์อ่านได้ |
| ความยาก | สูงกว่าข้อ ๑ — ขั้นตอนแรกคือการหาช่องทาง ยังไม่ใช่การเขียนโค้ด |
| เงื่อนไข | ❌ ถ้าหาช่องทางที่อ่านผลได้ไม่พบ ต้องหยุด ไม่ใช่เดา |

::: warning ลำดับสำคัญ
ทำข้อ ๑ ก่อนข้อ ๒ เสมอ เพราะข้อ ๑ มีข้อมูลพร้อมแล้ว ส่วนข้อ ๒ ยังต้องค้นหาก่อน
:::

### ๓. คุยผ่าน LINE — R16

| หัวข้อ | รายละเอียด |
|---|---|
| เหตุผลที่ทำ | พี่ฆังใช้ LINE เป็นช่องทางหลัก ความต่อเนื่องจะดีขึ้นมาก |
| สิ่งที่ต้องทำ | webhook + bridge ที่แปลงข้อความเป็นคำสั่งของ Crew |
| สิ่งที่ตรวจแล้ว | ❌ LINE **ไม่ใช่ช่องทางในตัว** ของ Kiro Crew ต้องเขียนเอง |
| ความยาก | สูง — มี webhook, การยืนยันตัวตน, การจับคู่ผู้ใช้ และการส่งกลับ |
| หมายเหตุ | ต่างจาก Discord ตรงที่ LINE ไม่มี allowlist แบบ DM ต้องออกแบบการยืนยันตัวตนใหม่ |

::: danger ข้อนี้กระทบความปลอดภัยโดยตรง
LINE เป็นช่องทางสาธารณะมากกว่า DM ของ Discord
ต้องมีการยืนยันตัวตนผู้ใช้ก่อนสั่งงานได้เสมอ ห้ามสร้างช่องทางที่รับคำสั่งจากคนที่ไม่ยืนยันตัวตน
:::

### ๔. หน้าจอ System เพิ่มการแจ้งเตือน

| หัวข้อ | รายละเอียด |
|---|---|
| เหตุผลที่ทำ | ทรัพยากรหมดเป็นปัญหาที่ต้องรู้ก่อน ไม่ใช่หลังเสียแล้ว |
| สิ่งที่ต้องทำ | แจ้งเตือนเมื่อ RAM/ดิสก์ขึ้นเกินเกณฑ์ |
| ข้อมูลพื้นฐาน | RAM ทั้งหมด 30 GiB · ว่าง 25 GiB · ดิสก์ว่าง 51 GB |

### ๕. ปรับแนวทางการใช้งานจริง

| เรื่อง | สิ่งที่ควรทำ |
|---|---|
| งานที่ทำซ้ำ | ทำเป็น profile ใน `profiles/` เพื่อลดเวลาตั้งค่า |
| งานที่ต้องใช้ความเสี่ยง | สร้าง profile แคบ ๆ เฉพาะงานนั้น ไม่ใช้การเปิดกว้าง |
| เหตุการณ์ที่พลาด | บันทึกเป็นรายการคำสั่งต้องห้ามเพิ่ม |
| งานที่ AI ทำผิดซ้ำ ๆ | ปรับ profile หรือคำสั่งต้องห้าง ไม่ใช่สั่งซ้ำไปเรื่อย ๆ |

## ส่วนที่ ๓ — สิ่งที่ดูแลเป็นประจำ

| ความถี่ | ตรวจอะไร | ถ้าพบปัญหา |
|---|---|---|
| ทุกครั้งที่อัปเดตเครื่องมือ | ทดสอบ R1–R6 อีกครั้ง | รุ่นใหม่อาจเปลี่ยนพฤติกรรม sandbox |
| ทุกครั้งที่เพิ่ม backend | ทดสอบว่าคำสั่งต้องห้างยังบังคับใช้ | backend ใหม่อาจมีช่องทางหลุดใหม่ |
| ทุกเดือน | ตรวจ `kirocrew doctor` | แก้ปัญหาที่ขึ้น |
| เมื่อรุ่นเครื่องมือออกใหม่ | อ่านบันทึกการเปลี่ยนแปลงก่อนอัปเดต | อย่าอัปเดตแบบด่วน ๆ ในระบบที่ทำงานจริง |

### แผนสำรอง

| เรื่อง | วิธีจัดการ |
|---|---|
| คอนฟิกของระบบ | สำรอง `~/.kiro/crew/` เป็นระยะ โดยไม่เอา `.env` ไปเก็บที่อื่น |
| นโยบายความปลอดภัย | เก็บสำเนาไว้ เผื่อต้องย้อนกลับ |
| ประวัติการทำงาน | ตัดสินใจเองว่าเก็บนานแค่ไหน เพราะเก็บไว้นานคือเก็บข้อมูลงานจริงไว้นาน |

::: warning กฎเรื่อง secret ยังใช้เสมอ
แม้แผนสำรองจะไม่เอา `.env` ไปเก็บที่อื่น ก็ยังห้ามคัดลอกโทเคนลงในไฟล์สำรองที่แชร์ต่อได้
และถ้าเคยหลุดให้ถือว่ารั่ว ต้องออกใหม่
:::
