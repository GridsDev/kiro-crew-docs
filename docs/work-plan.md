## ระยะที่ ๐ — ตรวจสภาพก่อนติดตั้ง

**ยังไม่เปลี่ยนระบบใด ๆ** อ่านอย่างเดียว เพื่อยืนยันว่าสภาพจริงตรงกับที่คาดไว้ก่อนเริ่ม

### ตรวจอะไร

| ตรวจ | ทำไม |
|---|---|
| `tailscale serve status` | บันทึก route เดิมไว้ก่อนแตะ เพื่อยืนยันว่าไม่กระทบ `:8443` |
| `kirocrew tailnet status` | ดูว่า Crew จะ publish ที่ port ไหน และเปิด trust อยู่หรือยัง |
| `kiro-cli --version` | ยืนยันรุ่นและความเข้ากันกับ Crew |
| `kiro-cli acp --help` | ดูว่ารองรับโปรโตคอลตรงทางหรือไม่ |
| พอร์ตที่จะใช้ | ยืนยันว่า `5476` ยังว่าง |
| สิทธิ์เขียน route | เขียนได้จริงหรือไม่ |
| รหัสผ่าน sudo | ใช้ได้จริงหรือไม่ โดยไม่แสดงค่า |
| ทรัพยากร | ยืนยันว่ายังพอก่อนติดตั้ง |

### จุดหยุด
รายงานผลให้พี่ฆังทราบ **ก่อนติดตั้ง** ถ้าพบปัญหา หยุดแก้ก่อนขั้นถัดไป

::: tip สำคัญ
ถ้าพบว่าสิทธิ์ Tailscale เขียน route ไม่ได้ ให้เปลี่ยนวิธีเข้าถึง แล้วคุยกันก่อนขั้นที่ ๔ — ไม่ใช่ฝืนทำต่อ
:::

## ระยะที่ ๑ — ติดตั้ง Kiro Crew

### สิ่งที่ต้องได้

| ไฟล์/โฟลเดอร์ | หน้าที่ |
|---|---|
| `~/.kiro/crew/` | ที่เก็บข้อมูลทั้งหมด |
| `~/.kiro/crew-venv/` | สภาพแวดล้อม Python ที่จัดการเอง |
| `~/.kiro/crew-python/` | Python ที่จัดการเอง |

### ขั้นตอน

1. ติดตั้ง Kiro Crew ผ่าน Kiro CLI
   ```bash
   kiro-cli crew -y
   ```
   `kiro-cli` จะติดตั้ง Crew ให้เองถ้ายังไม่มี

   ::: danger URL ที่เคยเขียนผิด — ห้ามใช้
   `curl -fsSL https://download.kiro.dev/cli.sh | sh` เป็นตัวติดตั้ง **kiro-cli** เท่านั้น **ไม่ใช่ Kiro Crew**
   ถ้าทำตาม URL นี้จะได้แค่ `kiro-cli` แล้วเข้าใจผิดว่าติดตั้งครบ
   :::

   ตรวจจริงบน sv (3 ต.ค. 2569) ใช้ `kiro-cli crew -y -- --help` เพื่อให้เห็นรายการคำสั่งของ Crew ทันทีโดยไม่ต้องเปิดหน้าแชท

2. ตรวจสุขภาพทันที
   ```bash
   kirocrew doctor
   ```
   ใช้ `kirocrew <คำสั่ง> </dev/null` เสมอเมื่อรันผ่าน SSH — กันไม่ให้ค้างรอเมาส์
3. ตรวจว่าสร้างครบทุกส่วน และดูว่าอะไรถูกเพิ่มเข้า `~/.kiro/`

   ตรวจจริงบน `sv` (3 ต.ค. 2569): ได้ `crew/`, `crew-venv/`, `crew-python/`, `agents/`, `settings/` · symlink `crew-venv-current`
   สิ่งที่ยัง**ไม่ถูกสร้าง** และต้องทำเองในระยะที่ ๒–๓: `config.json`, `.env`, `security_policy.json`, `profiles/`
   (Crew สร้าง `~/.kiro/agents/kirocrew*.json` ให้เอง 11 ไฟล์ตอน spawn — นั่นคือของมัน ไม่ใช่การตั้งค่าของเรา)

### ต้องระวัง

- ครั้งแรกจะดาวน์โหลดโมเดลฝังประมาณ **610 MB** — เผื่อเวลาและเน็ต
- **อย่าใส่โทเคนในขั้นนี้** — ยังไม่มี Discord
- ถ้าคำสั่งติดตั้งมีอะไรที่ไม่คาดคิด ให้หยุดและถามก่อน อย่ากดยืนยันเอง

### จุดหยุด
รายงานผล `doctor` ให้พี่ฆัง รอก่อนขั้นที่ ๒

## ระยะที่ ๒ — ตั้งความปลอดภัย

ขั้นนี้สำคัญที่สุดของทั้งแผน เพราะเป็นขั้นที่ทำให้ AI ทำงานกับไฟล์จริงได้

### ตั้งค่าหลัก

| ค่า | เป็นอะไร | ทำไม |
|---|---|---|
| `agent.approval_mode` | `interactive` | ต้องอนุมัติก่อนทำงานที่มีผล |

ค่า sandbox ไม่ต้องตั้งเอง — `auto` จะเลือก `strict` ให้เองถ้าเครื่องรองรับ
แต่เครื่องนี้ยังไม่รองรับ จึงต้องแก้ที่ AppArmor profile ก่อน (ดูหัวข้อถัดไป)

::: danger ค่าเริ่มต้นของระบบคือ `auto` ไม่ใช่ `interactive`
ตรวจจริงจาก `kirocrew doctor` บน sv: `approval: auto`
ค่านี้มาจาก `defaults.json` ที่ติดมากับ Crew และ **ยังไม่ได้ถูกเปลี่ยน**
ตอนนี้ยังไม่ได้ตั้งค่าใด ๆ ใน `config.json` — เอกสารเดิมเขียนว่า `interactive` เป็นค่าเริ่มต้น ซึ่ง**ไม่ตรงกับของจริง**

**ผลกระทบ:** ถ้าปล่อยไว้ตอนนี้ งานที่มีผลกับระบบจะทำงานแบบไม่ต้องรอคนอนุมัติ
ต้องตั้ง `agent.approval_mode = interactive` ในขั้นนี้เสมอ
:::

### แก้บล็อก AppArmor ก่อน (ต้องใช้ sudo → ขออนุมัติก่อน)

> **สถานะจริง 3 ต.ค. 2569 — แก้เสร็จแล้ว** ตารางข้างล่างเป็นค่า **ก่อนแก้**
> ผลหลังแก้: [๕. การตรวจสอบ ข้อ ๙.๑](/verification)

ตรวจแล้วบน `sv` พบว่า probe ของ sandbox ล้มจริง ไม่ใช่ความบังเอิญ

| ข้อเท็จจริง | ค่าก่อนแก้ | ค่าหลังแก้ |
|---|---|---|
| `kernel.unprivileged_userns_clone` | `1` | `1` |
| `kernel.apparmor_restrict_unprivileged_userns` | `1` ← ตัวที่ทำให้ strict ใช้ไม่ได้ | `1` (แก้ที่ AppArmor profile ไม่ได้แก้ค่า kernel) |
| ผลที่เจอ | `unshare(CLONE_NEWNS) failed with errno 1 (EPERM)` | ✅ `unshare -U true` ผ่าน |
| profile ปัจจุบัน | ไม่มี launcher profile (`kirocrew sandbox status`) | ✅ `/etc/apparmor.d/kirocrew-userns` |
| service | ยังไม่มี `kirocrew.service` | ✅ **system-level** ที่ `/etc/systemd/system/kirocrew.service` · `enabled` / `active` |
| คงอยู่หลังออกจากระบบ | `Linger=no` | ไม่เกี่ยว — system service เปิดพร้อม boot โดยไม่ต้องเปิด linger |

คำสั่งทางการของ Crew เองสำหรับงานนี้ — **ต้องได้รับอนุมัติจากพี่ฆังก่อนทุกคำสั่ง**

ตรวจจาก `kirocrew sandbox install-profile --help` แล้ว `--path` หมายถึง *executable ที่จะผูก profile* ค่าเริ่มต้นคือ `$APPIMAGE`
แต่เครื่องนี้ติดตั้งแบบ venv/pip จึงไม่มี `$APPIMAGE` และ `sandbox status` แนะนำให้ใช้ `service install` แทน

```bash
# 1) ตรวจสถานะก่อน — ไม่ต้องใช้ sudo
kirocrew sandbox status

# 2) ขั้นตอนที่ต้องทำก่อน Crew จะยอมติดตั้ง profile
#    /home/devg/.kiro เดิมเป็น 775 (กลุ่มเขียนได้) → ลดเป็น 750
chmod 750 /home/devg/.kiro

# 3) ทางที่ Crew แนะนำสำหรับเครื่องที่ไม่ใช่ AppImage — ต้องใช้ sudo
#    ✅ พี่ฆังอนุมัติและรันผ่าน sv.py แล้ว 3 ต.ค. 2569
kirocrew service install

# 4) ทางเลือก: ผูก userns profile กับตัว kirocrew โดยตริด — ต้องใช้ sudo
#    ยังไม่ได้รัน เพราะขั้นที่ 3 แก้ปัญหาได้แล้ว
kirocrew sandbox install-profile --path /home/devg/.local/bin/kirocrew

# 5) เปิดให้ service อยู่ต่อหลัง logout — ต้องใช้ sudo
#    ❌ ไม่จำเป็นแล้ว เพราะเป็น system service (ไม่ได้รัน)
loginctl enable-linger devg
```

::: tip ข้อ ๒ คือก้าวที่ตกไปจากแผนเดิม
แผนเดิมไม่ได้คาดคิดว่าจะต้องลดสิทธิ์ — Crew ปฏิเสธ profile ด้วยข้อความว่า
`/home/devg/.kiro` เขียนได้โดยกลุ่ม ทำให้ผู้ใช้อื่นในเครื่องที่ login ได้สามารถแทรกไฟล์ปลอมเป็น executable ได้
ต้องตรวจ `getent group devg` ก่อนลดสิทธิ์ทุกครั้ง
:::

::: tip ไม่ต้องหา binary ชื่อ `kiro`
`gateway.log` ขึ้นว่า `Command: kiro` แต่ตรวจแล้ว **ไม่มีไฟล์ชื่อ `kiro` บนเครื่อง** และไม่ต้องมี
คำนั้นคือชื่อ helper ภายในแพ็กเกจที่ Crew พิมพ์มาในข้อความเตือนเท่านั้น
ตัวจริงที่ต้องผูกคือ `kirocrew` (`/home/devg/.local/bin/kirocrew`) — ดูหลักฐานใน [๕. การตรวจสอบ](/verification)

รอ `พี่ฆัง` อนุมัติก่อน ห้ามรันคำสั่งที่ใช้ sudo เอง
:::

### สร้างชั้นควบคุมสองชั้น

```
เพดานสูงสุด  security_policy.json      ← ห้ามเกินนี้เด็ดขาด
      ↓
กรองเฉพาะงาน  profiles/                ← แต่ละงานเข้มงวดยิ่งได้
      ↓
ผลที่บังคับใช้  = สิ่งที่ทั้งสองชั้นอนุญาตร่วมกัน
```

::: tip หลักการ
**เข้มงวดที่สุดเป็นผล** — ถ้าเพดานหนึ่งห้ามแต่ profile อนุญาต ผลคือ **ห้าม**
เพราะฉะนั้นงานที่อยากให้ทำเองได้ ต้องเพิ่มความยอมให้ทั้งสองชั้นพร้อมกัน ไม่ใช่แก้ที่ชั้นเดียว
:::

### ตรวจสอบนโยบาย

## ระยะที่ ๔ — เปิดผ่าน Tailscale

ทำให้เข้าถึง dashboard จาก Notebook ได้ โดย**ไม่ต้องเปิดสู่ภายนอก**

### หลักการ

| หัวข้อ | ค่า |
|---|---|
| ที่ฟังจริง | `127.0.0.1:5476` — ผูกเฉพาะ loopback |
| URL ภายนอก | ผ่าน Tailscale เท่านั้น |
| การยืนยันตัวตน | บังคับใช้โทเคนทุกคำขอ |
| อายุโทเคน | 20 ชั่วโมง |

### ขั้นตอน

1. **บันทึก state เดิมก่อนทุกอย่าง**
   ```bash
   tailscale serve status
   kirocrew tailnet status
   ```
2. **ทดสอบ route เดิมก่อน**ว่ายังใช้ได้
   ```bash
   curl -sS -o /dev/null -w '%{http_code}\n' https://sv.tail7b4d4a.ts.net:8443
   ```
3. เปิดด้วยคำสั่งของ Crew เอง — **ห้าม** เขียน `tailscale serve` เอง
   ```bash
   kirocrew tailnet up
   ```
   - `:8443` → `127.0.0.1:3001` ของ Billing ต้องยังใช้ได้เหมือนเดิม
   - Crew จะจัดการ trust/ACL/cert renewal เอง
4. ยืนยันว่า publish สำเร็จ
   ```bash
   kirocrew tailnet status
   ```
5. **ทดสอบ route เดิมอีกครั้ง** — ถ้า `:8443` เสีย ให้ `kirocrew tailnet down` ทันทีแล้วหยุด
6. สร้างโทเคนเข้า dashboard
   ```bash
   kirocrew token --ttl 20h
   ```

::: danger จุดที่ห้ามพลาด
- ถ้า route `:8443` ใช้ไม่ได้ แปลว่ากระทบงาน Billing ของพี่ฆัง → ปิด tailnet ทันที
- ห้ามใช้ `tailscale serve` เพื่อเพิ่ม route เอง เพราะจะไปชนกับสิ่งที่ Crew คาดว่าจะจัดการเอง
- ค่าเริ่มต้นจริงของ Crew คือ `auto` — ถ้ายังไม่ได้ตั้ง `interactive` ห้ามเปิดใช้งานจริง
:::

## ระยะที่ ๕ — ให้เป็น service

> **สถานะจริง 3 ต.ค. 2569 — เสร็จแล้ว แต่ต่างจากแผน**
> ใช้คำสั่งทางการ `kirocrew service install` แทนการเขียนไฟล์เอง
> ได้ **system-level service** ที่ `/etc/systemd/system/kirocrew.service` → `enabled` / `active`
> จึง **ไม่ต้องเปิด linger** และไม่ได้รัน `loginctl enable-linger devg`
> หลักฐานและกับดักตอนตรวจ: [๕. การตรวจสอบ ข้อ ๙.๑ และ ๙.๒](/verification)

### เหตุผลที่แผนเดิมคาดว่าจะเขียนไฟล์เอง

คำสั่งติดตั้ง service ต้องใช้สิทธิ์ระดับระบบ แต่เครื่องนี้ต้องใส่รหัสผ่านทุกครั้ง จึงวางแผนจะเลี่ยงมาด้วย **service ระดับผู้ใช้** ที่ทำงานได้โดยไม่ต้องใส่รหัสผ่านขณะรัน

::: tip ผลจริงต่างจากคาด
เมื่อได้รับอนุมัติแล้วจึงพบว่า **คำสั่งทางการของ Crew จัดการเรื่องนี้ให้เอง**
คำสั่งเดียวทำได้ทั้งการติดตั้ง systemd unit และ AppArmor profile — ไม่ต้องเขียน unit เอง
รายละเอียดความต่างทั้ง 4 ข้อ: [๕. การตรวจสอบ ข้อ ๔](/verification)
:::

### ขั้นตอน (ตามที่ทำจริง)

1. ตรวจว่าไม่มีอะไรพึ่งสิทธิ์กลุ่มของ `/home/devg/.kiro`
   ```bash
   getent group devg
   ```
   ผล: `devg:x:1000:` — ไม่มีสมาชิกอื่น มี user เดียวบนเครื่อง
2. ลดสิทธิ์ให้ Crew ยอมติดตั้ง profile (ขั้นนี้ไม่ได้อยู่ในแผนเดิม)
   ```bash
   chmod 750 /home/devg/.kiro     # 775 → 750
   ```
3. ติดตั้งผ่านช่องทาง sudo ที่กำหนด
   ```bash
   python3 sv.py "/home/devg/.local/bin/kirocrew service install"
   ```
4. ตรวจว่า sandbox ใช้ได้จริง — ดู [๕. การตรวจสอบ ข้อ ๙.๑](/verification)

### ยังต้องทดสอบ
**R8 — reboot จริง** ยังไม่ได้ทำ เพราะเป็น system service ที่ `enabled` แล้ว
แต่ยังไม่มีหลักฐานว่ากลับมาทำงานเองหลัง reboot — ห้ามบันทึกว่าผ่านจนกว่าจะเปิดเครื่องใหม่จริง
