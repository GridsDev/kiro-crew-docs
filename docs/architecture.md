# ภาคผนวก ก — สถาปัตยกรรม Multi-Agent

ข้อมูลไหลอย่างไร ตั้งแต่พี่ฆังพิมพ์คำสั่งแรกจนถึงคำสั่งบน `sv` ทำงานจริง

::: warning ติดตั้งแล้ว แต่ยังไม่ทำงานครบวงจร
ภาพนี้คือ **สถาปัตยกรรมที่ออกแบบไว้** — ส่วนที่ติดตั้งจริงบน `sv` คือ binary, data home, config, agent config และ consent file
ส่วน service, AppArmor profile, security policy, Discord และ tailnet ยังไม่มี ทุกชิ้นที่ยังไม่ยืนยันจะเขียนกำกับไว้ตรง ๆ
:::

║  │ ชั้นแคบ  : profiles/  ต่อหนึ่งงาน                     │  ║

::: tip อ่านแผนภาพนี้
จากบนลงล่างคือ **เส้นทางที่ความน่าเชื่อถือลดลงเรื่อย ๆ**
ทุกชั้นที่ลงมากยิ่งแคบลง ยิ่งผ่านได้ยากขึ้น
ระบบที่ออกแบบดีคือระบบที่ทำให้ชั้นล่างไม่จำเป็นต้องกว้าง — ไม่ใช่ระบบที่ชั้นบนตรวจเยอะ
:::

## ชั้นที่ ๑ — Discord

ช่องทางเดียวที่พี่ฆังใช้สั่งงาน เลือกเป็นช่องทางหลักเพราะใช้บนมือถือได้จริง

| คุณสมบัติ | รายละเอียด |
|---|---|
| การยืนยันตัวตน | **ปิดเป็นค่าเริ่มต้น** — ต้องอยู่ใน `discord.allowed_user_ids` |
| การเชื่อมต่อ | Gateway WebSocket ฝั่งเข้า · REST ฝั่งออก — ไม่ต้องเปิดพอร์ตเข้า |
| ข้อความยาว | ตัดที่ ๒๐๐๐ ตัวอักษร · ระบบแบ่งให้เอง |
| อนุมัติคำสั่ง | ปุ่มในตัวข้อความ · หมดเวลา ๒ ชั่วโมง = ปฏิเสธอัตโนมัติ |
| ไฟล์จากคนนอก allowlist | ทิ้งเงียบ ไม่มีแจ้งเตือน |

**ทำไมเลือก Discord ไม่ใช่ Slack** — Slack ใช้ Owner ID คนเดียวเป็นตัวล็อก ส่วน Discord ใช้รายการยอมรับต่อคน เพราะการชวนบอทเข้าเซิร์ฟเวอร์สาธารณะทำได้ง่าย ถ้าไม่มี allowlist บอทจะเปิดกับทุกคนที่ DM ได้

## ชั้นที่ ๒ — Session

หนึ่งผู้ใช้หนึ่ง session ต่อเนื่อง ไม่ใช่หนึ่งห้องสนทนาหนึ่ง session

```
ผู้ใช้คนเดียว
   │
   ├─ DM เรื่องที่ ๑ ──┐
   ├─ DM เรื่องที่ ๒ ──┼──► session เดียวกัน  จำบทสนทนาได้
   └─ DM เรื่องที่ ๓ ──┘

คนที่สอง ──────► session แยก ไม่เห็นบทสนทนาของคนแรก
```

## ชั้นที่ ๓ — Agent Backend

| ตัวเลือก | บทบาท | สถานะ |
|---|---|---|
| **Kiro CLI** | ตัวหลัก — คุยผ่าน ACP | ⏳ ยังไม่ยืนยันว่าเข้าคู่กับ Crew บน `sv` ได้ |
| **OpenCode** | ตัวสำรอง | ⏳ ยังไม่ทดสอบโหมดสิทธิ์จริง |

::: warning ข้อจำกัดที่ยังไม่มีทางแก้ในตัวระบบ
งานที่รันอัตโนมัติโดยไม่มีคนอยู่กดอนุมัติ **ใช้เครื่องมือไม่ได้** ในโหมด interactive
ถ้าจะให้ใครเข้ามาใช้ Discord เป็นคนที่สองต่อ ต้องยอมรับข้อจำกัดนี้ก่อน
:::

## ชั้นที่ ๔ — ความปลอดภัยสองชั้น

นี่คือหัวใจของทั้งระบบ

```
security_policy.json          ชั้นกว้าง — เพดานสูงสุดของทั้งระบบ
┌──────────────────────────────────────┐
│ แตะไฟล์ทั้งระบบ        → อนุญาต      │
│ ลบไฟล์ระบบ              → ห้าม        │
│ ใช้เครือข่ายนอก          → อนุญาต      │
│ ส่งข้อมูลออกนอกเครื่อง   → อนุญาต*     │
└────────────────┬─────────────────────┘
                 │  ตัดกรองต่อ
                 ▼
profiles/  ชั้นแคบ — เฉพาะงานนั้น
┌──────────────────────────────────────┐
│ ตัวอย่าง: งานปรับปรุงเอกสาร         │
│   อ่านไฟล์ .md        → อนุญาต      │
│   แก้ไฟล์ .md         → อนุญาต      │
│   รันคำสั่งระบบ        → ไม่อยู่ในโปรไฟล์ = ถูกปฏิเสธ │
└────────────────┬─────────────────────┘
                 │
                 ▼
          ผลลัพธ์จริง = สิ่งที่ทั้งสองชั้นอนุญาตร่วมกัน
```

::: info ทำไมชั้นแคบถึงปฏิเสธ ไม่ใช่แค่ "ไม่อยู่ในรายการ = อนุญาต"
นี่คือหลัก **ปิดเป็นค่าเริ่มต้น** — ต้องมีการระบุว่าอนุญาตอะไรชัด ๆ อย่างเดียว
ถ้าปล่อยให้ "ไม่อยู่ในรายการ = ได้" ชั้นแคบจะกลายเป็นของที่ไม่ได้จำกัดอะไรเลย
:::

## ชั้นที่ ๕ — Sandbox

| ค่า | ผล | สถานะจริงบน `sv` |
|---|---|---|
| `agent.sandbox = strict` | คำสั่งนอกขอบเขตถูก **ปฏิเสธ** ไม่ใช่ถาม | ค่าเริ่มต้นที่ตั้งใจจะใช้ แต่ **ยังไม่ได้ตั้ง** |
| `agent.approval_mode = interactive` | เรียกเครื่องมือทุกครั้งต้องได้รับอนุมัติ | ยังไม่ได้ตั้ง — ระบบยังใช้ค่าเริ่มต้น `auto` |

::: info ค่าที่ตั้งไว้คือ `agent.sandbox = auto` แต่ตอนนี้มันทำงานแบบ strict แล้ว
`auto` คือ "ใช้ strict ถ้าเครื่องรองรับ" — เดิมเครื่องนี้ probe ไม่ผ่าน
เพราะ `kernel.apparmor_restrict_unprivileged_userns = 1` ได้ `unshare(CLONE_NEWNS) failed with errno 1 (EPERM)`
แก้แล้ว (3 ต.ค. 2569) ด้วย `chmod 750 /home/devg/.kiro` แล้ว `kirocrew service install` (ผ่าน `~/python-tools/sv.py`)
→ `unshare -U true` ผ่าน และ `SandboxUnavailableError` = 0
ตรวจค่าจริงได้ด้วย `kirocrew config get agent.sandbox` — ค่ายังเป็น `auto` แต่ผลที่ได้คือ strict
:::

::: danger เรื่องที่คนส่วนใหญ่จะถูกล่อ
มีคนจะบอกว่า "ให้ถอด strict ไปเลย จะได้ทำงานได้" — **ห้าม**
ทางแก้ของปัญหา Git SSH คือ consent ไม่ใช่การถอดกรอบทั้งระบบ
ถอด strict เท่ากับเอากำแพงทั้งหมดออกเพื่อแก้ประตูหน้าเดียว
:::

## เส้นทางหนึ่งคำสั่ง

ตัวอย่างคำสั่งจริง — "อ่านไฟล์นี้แล้วสรุปให้หนึ่งย่อหน้า"

```
พี่ฆังพิมพ์ใน Discord
        │
        ▼
① Discord รับข้อความ
   ตรวจ: User ID อยู่ใน allowlist ไหม?
   └── ไม่อยู่ → ทิ้งเงียบ จบที่ตรงนี้
        │ อยู่
        ▼
② เปิดหรือต่อ session เดิม
   หมดอายุไปหรือยัง? (๖๐ นาที)
        │
        ▼
③ เลือก agent backend (Kiro CLI)
        │
        ▼
④ agent ตัดสินใจว่าจะใช้เครื่องมือ
   ขออ่านไฟล์ → ต้องผ่านชั้นความปลอดภัย
        │
        ▼
⑤ ส่งปุ่มอนุมัติกลับไปที่ Discord
   พี่ฆังกด Approve
        │
        ▼
⑥ ทำงานจริงบน sv (อยู่ใน sandbox)
        │
        ▼
⑦ สรุปคำตอบกลับ Discord
   ถ้ายาวเกิน ๒๐๐๐ ตัวอักษร → แบ่งส่ง
```

::: tip จุดที่พี่ฆังมีอำนาจจริง
ขั้นตอนที่ **๕** คือจุดเดียวที่พี่ฆังหยุดงานได้
ทุกขั้นอื่นเป็นการดำเนินการอัตโนมัติที่อยู่ภายใต้กรอบที่ตกลงไว้แล้ว
ถ้ากด Reject ระบบจะหยุดและไม่ทำต่อ ไม่ใช่ลองวิธีอื่นแทน
:::

## สิ่งที่เลือก **ไม่** ใช้

| ไม่ใช้ | เหตุผล |
|---|---|
| Discord เป็นช่องทางสาธารณะ / เซิร์ฟเวอร์ใหญ่ | เปิดกว้างเกินจำเป็นสำหรับงานลับ |
| เปิดพอร์ตเข้าโดยตรง | ไม่ต้องมี — Gateway ต่อเอง |
| สิทธิ์ Administrator | ไม่จำเป็นสำหรับ DM และเป็นความเสี่ยงฟรี |
| LINE / Slack เป็นช่องทางหลัก | ยังไม่มีช่องทางที่คุมได้ รอคุยก่อน |
| `agy` / Copilot เป็น agent หลัก | ไม่มีช่องทางที่คุมได้ ถือว่าความเสี่ยงสูง |
| ราคาและโควตาที่ยังไม่ตรวจ | ห้ามอ้างตัวเลขที่ไม่ได้ยืนยันจากบัญชีจริง |

## ส่วนที่ยังไม่รู้ว่าจะเป็นอย่างไร

| ส่วน | สิ่งที่ยังไม่รู้ |
|---|---|
| Agent ที่ใช้จริง | Kiro CLI 2.26.0 เข้าคู่กับ Crew/ACP บน `sv` ได้หรือไม่ |
| การทำงานหลัง reboot | user systemd จะทำงานต่อเนื่องหรือไม่ |
| การเข้าถึง dashboard | `kirocrew tailnet up` จะกระทบ route `:8443` ของ Billing หรือไม่ — ยังไม่ทดสอบ |
| เสถียรภาพเมื่อหลายคนใช้ | ยังไม่เคยทดสอบพร้อมกัน |
| ต้นทุนและโควตา | ไม่ทราบจนกว่าจะตรวจบัญชีจริง |
